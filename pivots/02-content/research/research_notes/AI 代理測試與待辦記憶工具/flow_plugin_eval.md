## Q1. What is flow, where does it keep state, and can Codex or OpenCode use it?

### Takeaway
flow is a Claude Code "hooks module" that turns the main session into a super-manager that starts per-task manager agents and worker agents (one git worktree and one PR each), plus a reviewer that merges, runs the full check, releases and deploys. Its state lives in `<git-common-dir>/flow/` (for BuildClub: `/Users/tommy/Desktop/BuildClub/.git/flow/`), which is machine-local, never committed and not visible to a teammate or another machine. Codex, Gemini and OpenCode can only be workers that flow launches in an Orca or tmux terminal; they do not load the plugin, so none of its hooks, guards or memory apply to them.

### Cited Findings
- Roles and flow of work: main session with the `dispatch` skill -> `flow:manager` per task (pre-flight questions, briefs, PR review) -> `flow:worker` per piece (own worktree, opens PR) -> `flow:reviewer` (merge, full check, release, push, deploy gates). Agents exist as `flow:manager`, `flow:worker`, `flow:reviewer`, `flow:continue` (continues a handed-off branch) and `flow:queue` (old name of reviewer). — `/Users/tommy/.claude/plugins/cache/flow/flow/0.6.123/README.md`, `skills/dispatch/SKILL.md`
- Skills: `flow:init` (onboarding, demo, settings) and `flow:dispatch`. Commands: `/flow`, `/flow inbox`, `/flow ok`, `/flow no`, `/flow answer`, `/flow checks`, `/flow approve`, `/flow reject`, `/flow push`, `/flow hold`, `/flow release`, `/flow lite`, `/flow resume`, `/flow clean`, `/flow-tasks`. — README "A day with flow"
- Tools (MCP-style, registered by the hook): `ask`, `fyi`, `answer`, `check`, `clean`, `deploy`, `guard_tests`, `handover`, `migrations`, `note`, `plan`, `preflight`, `release`, `reviewer`, `session`, `status`, `test_slot`; main-only deferred: `standing`, `push`, `queue`; others in this session's tool list: `settings`, `demo`, `arms`, `decide_eval`, `size_ab_report`. — `docs/reference.md` "Tools the agents use"
- State directory and files: `handovers/<pr>.json`, `log.jsonl` (append-only events), `handoffs/<branch>/<n>.md` (transcript digest of a worker's handoff), `managers/<key>/notes.md`, `push.json`, `preflight.json`, `checks.json` (person checks), `ledger.json` (token cost per agent and model), `inbox.json`, `config.json` (personal settings and standing answers), `init-done`, `test-slots/`, `sessions/<name>/report.md`. "shared by all worktrees, never committed". — `docs/reference.md` "State on disk", README "What it writes"
- On this machine the BuildClub state is only: `ledger.json` (222 KB, 614 entries: 68 `main@...` and 546 other agents, including ordinary general-purpose subagents), `log.jsonl` (6 lines), `seeds-offered.json`, `test-slots/`. — `/Users/tommy/Desktop/BuildClub/.git/flow/`
- The only repo-level (shareable, committable) part is the settings file `.claude/flow.json` (and optional task-source docs under `.claude/flow/sources/`). BuildClub has no `.claude/flow.json`; the user's only flow setting is `main_checkout_allow: ".claude/, research/"` in the global Claude settings. — `docs/reference.md` "Settings per repo", `/Users/tommy/.claude/settings.json` (pluginConfigs)
- Standing answers go to the personal file `.git/flow/config.json` (machine-local); copying them into `.claude/flow.json` shares them. flow "never edits the committed file". — `docs/how-it-works.md` "Standing answers", `docs/reference.md` "Guard tests"
- Claude-only runtime: it is a hooks module that registers tools through the engine (`session.start`, `tool.call`, `agent.spawn`, `turn.step`, `turn.complete`). — README "Its hooks"
- Other harnesses: `mcp__flow__session` can start a worker in `claude`, `codex`, `gemini`, `opencode` or a custom command, but only in `mode` orca or tmux (default `mode` is `agent`, where a session start is refused). They run with permission checks off (`codex --dangerously-bypass-approvals-and-sandbox`, `gemini --yolo`, `claude --permission-mode bypassPermissions`). A non-Claude harness "loads no plugin and has none" of the flow tools; "Workers started in other harnesses do not pass through the hook, so only the worker prompt applies to them". Reports return by a file `sessions/<name>/report.md`; Codex quota is read from `~/.codex/sessions`. — `docs/how-it-works.md` "Workers in other harnesses", `docs/reference.md` "The test lock", "Without Orca"
- Limits stated by the author: everything runs inside one session; close it and work stops (branches and PRs stay, `/flow resume` picks up); all agents burn the same account's usage; the lock "covers every worktree of the session's agents, not other Claude sessions". — README "Limits", `docs/reference.md` "The test lock"

### Inferences
- Because state is under `.git`, it is shared across the user's own worktrees on one machine (good: the 36 BuildClub worktrees see one ledger and one slot pool) but invisible to the teammate, to a second Mac, and to any tool that does not look in `.git/flow`. The files are plain JSON and Markdown, so Codex could read them if told to; nothing tells it to.
- "Can Codex use it" splits into: (a) as a worker launched by flow: yes, with no guard rails; (b) as an independent session that benefits from flow's memory, locks or guards: no.

### Gaps
- I did not verify whether Orca's `mode: orca` terminals work well with the user's Orca setup; the docs say it needs `orca status` reachable.
- I could not check what `settings` / `demo` / `decide_eval` / `size_ab_report` / `arms` do beyond their docs: `arms` = best-of-N competing workers, `decide_eval` and `size_ab_report` = measure the model-size routing, `demo` = onboarding demo cleanup. None of these touch the user's problem categories.

## Q2. How has the user actually used flow in BuildClub, and how did it go?

### Takeaway
The user has used only the passive, always-on guard layer. In 9 days, 31 top-level sessions and many subagents called `test_slot` (about 390 acquire/release pairs, mostly for `tsc` and `verify.sh`) and `guard_tests` 15 times; flow's hooks refused 228 tool calls. The user never started a flow manager, worker or reviewer, never used a `/flow` command, never used `ask`, `fyi`, `check`, `standing`, `handover`, `plan` or `note`. So none of flow's memory features (inbox, decisions, checks, standing answers, notes, resume) has been exercised on this project. I found no complaint about flow in the user's messages, and no sign the user knows the guards are flow's.

### Cited Findings
- Exact tool-use counts across all BuildClub transcripts 2026-10-27..11-04: `mcp__flow__test_slot` 784 calls (typecheck kind: 267 acquire + 260 release; no kind: 122 acquire + 123 release; kind "test": 4+4; 4 status), `mcp__flow__guard_tests` 15, `mcp__flow__status` 1. Zero calls of any other flow tool. Zero `Agent` spawns of `flow:*` types. Zero `/flow` slash commands in user messages. — structured parse of `/Users/tommy/Library/Application Support/orca/claude-profiles/0b0de81f-.../home/projects/*BuildClub*/**/*.jsonl`
- Reach: 31 distinct top-level sessions used `test_slot`/`guard_tests`/`status` (out of the 71 sessions in the earlier audit); activity by day: 10-27: 54, 10-28: 72, 10-29: 32, 10-30: 73, 10-31: 10, 11-02: 345, 11-03: 210, 11-04: 4 calls. Most are from subagents (153 of the 177 transcript files with flow calls are `subagents/` transcripts, 24 are main sessions), i.e. AI workers complying with the hook, not the user.
- What the slots wrapped: labels such as `tsc -b` (22), `verify.sh` (16), `tsc -b + lint` (12), `tsc` (10), `npm run build`, `bin/verify.sh`, `remake verify + e2e`, `trend-finder build`. — same transcripts
- Hook denials (tool results starting `flow:`): 228 total. 108 were `pkill`/`killall` refusals ("Every flow agent runs in this one Claude Code session..."), 109 were "`<cmd>` is a typecheck. Call mcp__flow__test_slot ... acquire first ... The slots are free, so acquire is instant", 11 were `kill` fed by `lsof` without `-sTCP:LISTEN`. Peak 82 denials on 2026-11-02, 37 on 11-03. — same transcripts
- Contention was low: 7 typecheck `acquire` calls returned "No typecheck slot after N s; queued, position N" (for example "Held by main (build a...)"), out of about 267. Releases with result "fail": 1 typecheck, 1 other. — same transcripts
- flow's own persisted evidence of a failing test: `log.jsonl` has one `tests-failed` event: 2026-10-30, agent "Run Task 11 TikTok gate", "tests: failed: e2e step 8 (pre-existing)". The other 5 log lines are automatic `clean` sweeps (removed merged branches such as `feat/node-canvas-p1` on 11-03 and a batch of `feat/remake-*` on 11-02). — `/Users/tommy/Desktop/BuildClub/.git/flow/log.jsonl`
- The single `mcp__flow__status` call (a Playwright verify subagent) returned only "Suggested starting rules (not applied)" (seeds `tracker`, `prod-env`), "No PRs handed over", a cleanup note ("1 holds work that isn't merged") and a cost block (for example main ~$1.51 and ~$2.52 at API list price, cache hit 97%). — same transcripts
- The seeds offer was shown once (`seeds-offered.json`) and no rule was ever added; the `tracker` seed (never write to an external task tracker without a yes) and `prod-env` seed (always ask before production changes) are the closest the plugin has to the user's "standing rules", and both are unapplied.
- No user message mentions flow as a tool, praises it or complains about it. The only "flow" hits are Figma/UX "flow map". The one visible friction is the 109 typecheck denials: each one is a wasted tool call and a retry turn for an AI that did not know about the slot, even when the denial text itself says the slots are free.

### Inferences
- Flow has so far acted as a quiet process-hygiene layer (memory-safe test runs, no mass `pkill`), not as the consistency/memory tool the user is evaluating. The 228 refusals suggest the guards do fire in real work (especially `pkill`: AI agents tried it 108 times), which is relevant to the user's shared-port problem (see category 5) but was never measured as having prevented a collision.
- Whether the full manager/worker/reviewer/inbox workflow would help is untested on this project; the evidence only covers the guard hooks.

### Gaps
- I did not extract the text returned by `guard_tests` (15 calls); no guard_tests mapping exists in the repo (no `.claude/flow.json`), so those calls most likely returned "no guard tests required", but I did not confirm it.
- I could not tell from transcripts whether the user's global CLAUDE.md, a hook text or the plugin's own injected text taught the subagents to call `test_slot`; the denial message is one source.
- The cost block in `ledger.json` is at API list price and counts every subagent, so it is not the user's real spend (subscription).

## Q3. Map flow against the 8 problem categories

### Takeaway
Of the 8 categories, flow covers none fully, partly covers 6, and barely touches 2 (parallel sessions/teammate changes, and handoff drift in the user's own handoff and STATUS files). The strongest matches are the cleanup sweep (worktree pile-up), merge/push confirmation (never merging into the teammate's main unasked), the mandatory `## Verification` section and guard tests (unverified claims, but only inside flow PRs), the person-check list (human-only follow-ups, only after deploys) and the per-agent cost ledger (token cost only). Almost every feature requires the work to run as flow managers and workers; the user's plain Claude sessions, which is how BuildClub work was actually done, get only the guard hooks.

### Cited Findings

Legend: Covered / Partly / Not. "Needs flow workflow" = only works when work is run through flow managers/workers/reviewer.

1. Progress loss and "where are we" — Partly.
   - `mcp__flow__status` / `/flow`: live tree of managers, workers, handed-over PRs, test slots, cost, open inbox. `/flow resume` lists open `flow/*` PRs, pushed branches with no PR, and leftover worktrees with unpushed work, then restarts one manager per task with its notes. `mcp__flow__note` stores manager decisions/progress in `managers/<key>/notes.md` (survives restarts). Context-limit handoff: at `context_warn_percent` (default 40%, 35% on a 1M window) an agent is told to commit "WIP handoff", push, write `## Handoff` (Done/Remaining/Decisions/Gotchas) into the draft PR and end with `HANDOFF: <branch>`; the plugin stores a transcript digest and starts `<name>-2`. State in the PR and in git is treated as primary. — `docs/how-it-works.md` "Continuing work", `docs/reference.md` "State on disk"
   - Matches the user's "rotate sessions at 40%" rule almost exactly, but only for flow's agents; the main session "can't be replaced" and only gets a toast. It does not write `docs/STATUS.md` or `~/.claude/handoffs/<repo>.md`, and it cannot see other, non-flow sessions or the user's 26 hand-written resume prompts.
2. Standing decisions, budgets, preferences — Partly.
   - `fyi`: an agent records a reversible choice it made; it appears in the inbox as a decision (ids `d1`...), the user keeps or undoes it (`/flow ok`, `/flow no d12 <what instead>`), and the owner agent is told. `standing` / `answer ... always:true`: a recurring question (by `topic` or regex) is answered automatically from then on, with escalate rules that force asking the user, and a `conservative` rule on by default. Suggestions appear after the user gives the same answer 3 times. Seeds: `tracker`, `prod-env`. — `docs/how-it-works.md` "Questions and the inbox", "Standing answers"
   - But standing answers answer agent questions; they do not store project facts or budgets ("fal balance US$10", "English-only video", "no mobile", "Apify quota"), have no supersession link, no expiry, no spend cap, and are not shown to ordinary Claude sessions at start. Stored in the personal `.git/flow/config.json` (this machine only) unless copied by hand into `.claude/flow.json`.
3. Unverified "tested" claims — Partly (strongest feature for this problem, narrow scope).
   - `handover` refuses any PR whose description lacks a valid `## Verification` section: `Ran:` (commands with results; must include every configured `worker_checks`/`always_tests` command), `Exercised:` (how it was run for real, or `n/a: <reason>`), `Not verified:` (a bare "nothing" or "n/a" is refused). Stored on the handover and repeated in the reviewer report. `guard_tests`: a map from changed paths to repo-wide tests the worker must run and list. The reviewer runs the full check once per batch at the merged sha, can bisect failures, reruns flaky files once, and can run a scripted `verify_command` after merge. `test_slot release` takes `result` pass/fail and exact `failed_tests`. — `docs/reference.md` "Tools the agents use", "Guard tests"; `docs/how-it-works.md` "Verification", "Reviewer rules", "Person checks"
   - Weak points: `Ran:` is text the worker writes; nothing checks that a matching run happened (the `test_slot` pass/fail is also self-reported). The model-case failure "PR says tested with fal in #38 but nobody ran it" would pass the format check if the worker wrote it under `Ran:`; the mandatory `Not verified:` section makes the honest version cheap but does not enforce it. Applies only to PRs handed over through flow; not to chat claims such as "this demo can search live".
4. Git / branch / repo / worktree mistakes — Partly to mostly covered inside flow's own worktrees.
   - `clean` (tool and `/flow clean`; auto sweep after each merged PR, on agent end, and occasionally on `status`): removes flow-made worktrees and local branches judged by ancestry and the PR head sha (so squash-merged branches are recognised), never with `--force`, keeps anything dirty, unpushed, locked, open-PR or in live use, and lists what it kept and why. The log shows it already ran 5 times on BuildClub (removing branches like `feat/node-canvas-p1`). Workers branch from fresh `origin/<base>` (`git worktree add -b flow/<name> ... origin/<base>`), which targets "wrong base / stale fork/main". Guards: no edits to the repo's main checkout while flow work exists (`main_checkout_guard`), no remote-branch deletes by subagents, no broad `pkill`. `merge_mode: confirm` holds every PR until `/flow approve <n>`; `push_mode: confirm` stops after the full check until `/flow push`; deploy targets can require a human yes. — `docs/how-it-works.md` "Cleanup", "Guards", "Merge mode", "Push gate"; README; log.jsonl
   - Not covered: the user's two-repo situation (own repo + teammate's fork/remote); flow assumes one `origin` and one base branch. The main session can still run `gh pr merge` itself. Worktrees not made by flow (the user's Orca worktrees, including the 36 now registered) are "the person's own: never read, listed or touched".
   - Friction with the user's rules: flow deletes local branches with `git branch -D` after its own merged check, while the user's global rule is lowercase `-d` only; flow's branches are named `flow/<name>`, while the user's rule says not to use AI/tool names as branch prefixes; workers push and the reviewer merges and pushes `<base>`, while BuildClub's CLAUDE.md says do not commit or push unless asked (superseded in practice by the memory "auto commit"). These are config-level conflicts worth raising, not blockers.
5. Parallel sessions and teammate changes — Not / minimal.
   - `test_slot` is a cross-agent lock for heavy runs, but "covers every worktree of the session's agents, not other Claude sessions", lives in plugin memory and "a plugin reload empties it". The `pkill`/`killall`/`lsof`-kill guard protects one session's agents from killing each other's processes; it fired 108 + 11 times on BuildClub. There is no port or browser-window registry, no "what did the other sessions and the teammate change since T" feed, and nothing watches the teammate's pushes; `gh` is used only for PR state. — `docs/reference.md` "The test lock", `docs/how-it-works.md` "Guards"
   - The 2026-11-03 collision (another session started a server on port 8871 and replaced the screenshot agent's) is exactly what a session-scoped lock does not cover.
6. Handoff / STATUS drift — Partly in design, not in the user's files.
   - flow's own handoff note lives in the PR description and `handoffs/*.md`; `resume` reconciles stored handovers with GitHub (a handover whose PR is merged counts as done), i.e. git wins over stored claims, the same principle as the user's rule. It does not read, check or write `~/.claude/handoffs/*.md` or `docs/STATUS.md`, and does not flag a handoff written before a later commit.
7. Human-only to-dos — Partly (after-deploy checks and env changes).
   - `check`: `needs a person: PR #n: <steps>` in a reviewer report becomes a durable item (`checks.json`, id `c1`...), listed by `/flow checks` (Try now / Needs install of X / Version unknown), closed with `pass`, `fail <note>` (creates a follow-up task for a manager) or `skip <why>`; optional `verify_command` lets the reviewer close it by running a script. `handover env`: env/secret changes (`secret: true` means the user sets the value; optional `login` step) become inbox items that block the deploy target until answered. Deploy, env, push and reviewer items are marked NEEDS YOU and never auto-answered. — `docs/how-it-works.md` "Person checks", "Deploying"; `docs/reference.md`
   - Limits: checks are born only from a reviewer's done report; env items need a configured deploy target ("a non-empty env is refused when no deploy target is configured"). A general "add the ElevenLabs and Gemini keys" or "tell me when the account is created" item with a link to the task it blocks has no entry point.
8. Test-run and cost memory — Partly: token cost yes, test memory no.
   - `ledger.json` records tokens per agent and model, with cost estimated at Anthropic API list prices, per manager, per PR (by branch, across sessions), per reviewer and "All time", shown in `status` and in the reviewer's done line; entries older than 90 days are dropped. Failed runs under `test_slot` are remembered by agent+label with their test names and tree, and a pass on the same label and tree after a fail is recorded as flaky (kept in memory and as a log event; the log had one such `tests-failed` line). — `docs/reference.md` "Cost meter", `hooks/testfail.ts`, `docs/how-it-works.md` "Reviewer rules"
   - Not covered: a durable "this test already passed on this commit, do not re-run" record (the slots hold no history, reset on reload, and a lease expires after 45 minutes); spend on external paid APIs (fal, Apify, ElevenLabs, Gemini); quotas and budgets; evidence paths. The token ledger is not the user's real spend (subscription plans differ, as the docs admit).

### Inferences
- Scoreboard (my judgement, not a measurement): Partly = 1, 2, 3, 4, 7, 8 (6 of 8); minimal = 5, 6 (2 of 8). Weighted by the earlier audit's rough shares (progress about 35%, decisions/budgets 15%, claims 8%, git/worktree 8%, parallel/teammate 12%, human todos 8%, test/cost 12%), flow's mechanisms address a meaningful part of 1, 3, 4, 7 and a small part of 2, 5, 6, 8 in the situations where the work goes through flow's workers. Outside that, only the guards apply.
- The central mismatch: flow solves "how do I run many AI workers safely and merge their PRs" and carries memory as a by-product inside that pipeline. The user's recurring pain is cross-session continuity for mostly single-agent, interactive work plus a teammate on another repo. Using flow for memory alone would mean adopting the whole manager/worker/reviewer way of working, including its token overhead (every flow agent inherits the session's skills, plugins and MCP servers; the README says to trim them) and its constraint that "everything runs inside one session".
- Two features are close to what the user hand-built: `check` (similar to `docs/todo.md`) and the `## Verification` section (similar to the `docs/test-log.md` "do not re-run" rule), but both are keyed to PRs rather than to commits, tests or sessions.

### Gaps
- I could not test any of this behaviour; claims come from documentation and from source headers. In particular I did not verify that standing answers or decisions would actually be injected into a new session.
- Not checked: how well `mode: orca` interacts with the user's Orca-managed worktrees (flow would create its own worktrees under `.claude/worktrees/` or via `orca worktree create`).

## Q4. Gaps, phrased as constructive suggestions the user could give the friend

### Takeaway
The most valuable additions would make flow's state useful without adopting the whole manager pipeline: a persistent, content-keyed test and spend ledger; a decisions/constraints store with supersession that is injected at session start; claim-versus-ledger checking for the Verification section; cross-session awareness (other sessions, teammate pushes, ports); and a way to share or read state from outside Claude Code. The foundations exist in the code (tree-keyed failed runs, a cost ledger, durable checks, a stable `.git/flow` directory).

### Cited Findings
These are suggestions, each tied to the evidence above; none is a verified plugin roadmap item.

1. Test and run ledger keyed by content, with cost and evidence. Write one row at every `test_slot release`: command/label, tree hash or hash of the files the test covers, result, duration, optional external cost, evidence path. Add a lookup ("has this passed on this tree?") and let the hook or reviewer suggest skipping a re-run. Persist it under `.git/flow/` (survives reload and the 45-minute lease). `hooks/testfail.ts` already stores the tree of a failed run, so the key exists. Matches category 8 and the user's `docs/test-log.md` rule.
2. External-spend ledger and budget. A `spend` record (service, estimate, hard cap, actual) plus a budget setting such as "fal US$10, today under US$1", with a hook that asks before a Bash/API call that matches a paid-service command pattern, the way `test_slot_commands` already matches suite commands. Gives the per-run price quote the user keeps re-stating (Apify estimate US$0.30 vs actual US$0.68). Extends the existing token cost meter.
3. Decisions and constraints with supersession. Extend `fyi`/`standing` from "answer to a question" to "fact with scope, date, `supersedes` and optional expiry" (for example "English-only video content" superseding the Mandarin docs), and inject the active list at `session.start` into every session, not only flow agents. Matches category 2 (7 "remember this" requests in 9 days).
4. Cross-check claims against the ledger. Let `handover` verify that each `Ran:` command has a matching ledger row at that head sha, and flag PR text or reports that say "tested" for something with no row. This turns the existing format check into evidence checking and directly targets the "PR says tested with fal, nobody ran it" case.
5. Use the memory features without managers. Offer a "state only" mode: inbox, decisions, checks, `status`, `clean`, `resume` for the user's plain sessions, with no worker spawning. The usage data shows the user only ever touched the guard layer; the entry cost of the full pipeline is the barrier.
6. General human-task items with blockers. Let `check` (or a sibling) be created by any agent or by the user at any time, not only from a reviewer's done report, with fields `needs` (key, billing, account), `blocks` (task or PR) and a reminder at session start. Allow the secret-style `env` request without a deploy target. Matches category 7 (ElevenLabs/Gemini keys, "tell me when the account is ready").
7. Cross-session and teammate awareness. A `since` view of what other sessions in this repo and other contributors pushed (commits and PRs by others, new remote branches, stale local remotes such as `fork/main`), and a lock for ports and processes that lives in a file under the git common dir so it spans separate Claude sessions, not only one session's agents. The `pkill` guard shows the need is real (108 refusals); the 8871 collision was another session.
8. Shareable and tool-neutral state. An export to a committed file (for example `.claude/flow/state.md`) for decisions, open checks and ledger summaries so the teammate and a second machine see them, and a small CLI (`flow checks list`, `flow ledger has ...`) that Codex or OpenCode can call, plus an `AGENTS.md` snippet. Today state is Claude-hook-only and `.git`-local, and non-Claude workers get no guards.
9. Handoff and STATUS integration. A wrap-up action that lists worktrees and merged branches for approval (the user's closing ritual), and a freshness check that compares a handoff's State lines or `docs/STATUS.md` against git and warns when a commit followed the last handoff write (category 6).
10. Configuration fit and lower friction. (a) Make the branch prefix configurable (the user's rule forbids tool-name prefixes) and let `clean` fall back to a safe `-d` where possible (the user's rule forbids `-D`). (b) Let a typecheck or suite under a free slot be auto-acquired by the hook instead of denied: 109 denials each cost a retry turn even though the denial message itself says "the slots are free". (c) Support a second remote/fork as a base (two-repo setups). (d) Make the permission-off terminal harnesses opt-in per worker, since the user's safety rules treat that as high risk.

### Inferences

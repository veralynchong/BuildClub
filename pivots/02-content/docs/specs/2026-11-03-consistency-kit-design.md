## 1. 為什麼做、做成什麼

Agency 幫同一個客戶每個月做好幾支短影音。現在每一鏡分鏡圖都是各自從文字生成，所以同一支片裡的主角、產品、店面，每一鏡長得都不一樣，同一個客戶的下一支片又得從頭來。研究的結論〔使用者〕是：一致性靠的是**每個客戶一套有名字的參考圖**，不靠訓練模型。2026 年各家產品都這樣做，我們清單上的圖片模型也都吃多張參考圖，而且幾乎不加錢。

要能演完的一句話〔使用者，研究 §3C〕：**上傳 1 張人像和 1 張產品照，6 鏡分鏡圖都是同一個人拿同一個杯子；同一個客戶的第二個 plan 不用重新上傳，也一樣。**

```
客戶套組（跨 plan）──▶ 畫布上的「套組」節點（這支片的卡司）──自動接線──▶ 每個分鏡圖節點
                                                                       │
                                                       分鏡圖當起始畫面 ▼
                                                                   AI 影片節點
```

分鏡圖階段就把長相鎖住；影片模型只要拿分鏡圖當起始畫面，不吃參考圖也能接得上〔使用者，研究 §2B〕。

## 2. 目標、非目標、反目標

**目標**
1. 每個客戶有一組套組：角色、產品、場景、風格四類項目，每項有名字、1–4 張圖、一行描述〔使用者〕。
2. 生成請求從「一張參考圖」改成「N 張參考圖，每張帶類型和名字」，fal 和 Gemini 兩邊的轉接層都照這個送〔使用者〕。
3. 畫布上有一個「套組」節點，選這支片要用哪些項目，系統自動接到每個分鏡圖節點；單一鏡頭可以取消個別項目〔使用者〕。
4. 套組改了，下游分鏡圖標「過期」，**不自動重跑**，沿用畫布規格 §5〔使用者〕。
5. 「整條跑完」（分鏡圖＋影片）也帶上套組〔我的決定：這是 demo 最常按的按鈕，現在後端直接拒絕帶參考圖，見 `generations.py:531`〕。

**非目標（這次不做）**
- LoRA 或任何模型訓練、靠 seed、用上一鏡的最後一格接下一鏡〔使用者，研究的「不做」列〕。
- 影片節點吃套組參考圖（reference-to-video）〔我的決定，見 §7〕。
- 加入 Nano Banana 2.1，或其他模型清單調整（Veo 已在 PR #39 換掉）〔我的決定：與套組無關，另開一個小 PR〕。
- 用鏡頭文字自動判斷「這一鏡該帶誰」（研究提到可以當升級，但沒有驗證過）。
- 「自動補側面」：用 AI 從一張正面圖生出側面圖。
- P3 品牌素材（logo、字型、主色）照原樣，不和套組合併〔使用者，研究 §1C〕。
- 手機版〔使用者，2026-11-02 起不做 390 寬〕。

**反目標（就算做到了也算失敗）**
- 一按就悄悄多花錢：參考圖幾乎不加錢，但如果某個模型的參考圖要另外收費，價格顯示必須算進去。
- 套組一改，整張畫布的分鏡圖就自動重跑。
- 線多到看不見畫布。8 鏡 × 3 張參考＝24 條線，正是研究說選項 B 不能單獨上線的原因。
- 超過模型上限的參考圖被默默丟掉，使用者卻不知道（違反畫布規格 §11.5 #5「不默默丟掉」）。
- 一個客戶的套組圖出現在另一個客戶的 plan 裡。

## 3. 現況（實作者要知道的）

路徑相對於 `pivots/02-content/app/trend-finder/`。所有畫布程式都還在一串沒合併的 PR（#28→#39）上，P2.5 的分支接在最新的那一條後面。

- **單一參考圖的限制**〔程式碼，2026-11-03 讀過〕：
  - 前端 `src/lib/canvas/ports.ts`：參考埠 `in:ref` 只能接一條線（`canConnect` 回 `canvas.conn.taken`）。
  - `src/lib/canvas/graph.ts` 的 `GenRequest.reference?: string`；`types.ts` 的 `Generation.inputs.reference`。
  - 後端 `generations.py`：`check()` 只接受一個 `ref`，而且必須是「這個 plan 裡已完成的圖片生成」（`one(idea_id, ref_id)`）。`input_hash` 裡也只有一個 `reference`。工作執行時（約第 329 行）會把它解析成一個路徑。
  - **後端轉接層其實已經支援多張**：`gen_providers.py` 的 `Job.references: list`，fal 會送成 `image_urls`，Gemini 會送成多個 `inline_data`。

- **客戶素材的前例**：`backend/brand.py`。品牌資料存在 client 紀錄上（`models.Client.brand`），logo 檔案放在 `media/brand/<clientId>/`，只有登入的員工能用這些路由，用 `ID_RE` 防路徑跳脫。套組照同樣的形狀做。
- `Idea.clientId` 已經存在（`src/types.ts:188`），所以從 plan 可以找到客戶。
- 「過期」機制已經有了：`NodeData.stale`。

## 4. 資料

### 4.1 客戶層：套組〔使用者，研究 §3A；欄位名是我的決定〕

存在 client 紀錄上，和 `brand` 並列：

```json
"kit": { "items": [
  { "id": "k_mia", "kind": "character", "name": "Mia",
    "note": "early 20s, short black bob, yellow hoodie",
    "images": ["ka_3f9x2q.png", "ka_8b1m0z.jpg"], "updatedAt": 1762156800 },
  { "id": "k_cup", "kind": "product", "name": "Matcha cup", "note": "white cup, green logo facing camera", "images": ["…"], "updatedAt": … },
  { "id": "k_shop", "kind": "place", "name": "Shop counter", "note": "", "images": ["…"], "updatedAt": … },
  { "id": "k_look", "kind": "style", "name": "Warm film", "note": "35mm, warm tones, soft light", "images": [], "updatedAt": … }
] }
```

- `kind`：`character | product | place | style`。
- `images`：1–4 張；風格項目可以是 0 張（只有文字描述）。圖片檔放在 `media/kit/<clientId>/`，接受 PNG / JPG / WebP，單張 ≤ 10 MB〔我的決定：logo 是 5 MB；照片比較大〕。
- `name` 必填、在同一個客戶裡不能重複，≤ 40 字；`note` ≤ 200 字。影片內容只做英文，所以 note 也預期寫英文；介面不擋中文。
- 刪除一個項目時，它的圖片檔一起刪掉〔我的決定〕。已經生成的圖不受影響，那些生成紀錄存的是自己的副本，見 §4.3。
- 單一客戶最多 20 個項目〔我的決定〕。

### 4.2 plan 層：這支片的卡司〔使用者〕

存在畫布 JSON 裡：

- 套組節點：`data.kitItems: string[]`，這支片要用哪些項目。
- 分鏡圖節點：`data.kitOff?: string[]`，這一鏡不要哪些項目。預設是空的，代表全部都帶〔使用者，研究 §3A〕。
  - 研究原本寫成卡司底下的 `perShot` 對照表；放在節點上，畫布規格的「改了上游，下游過期」規則就能直接沿用〔我的決定〕。

### 4.3 生成請求〔使用者，研究 §3A；形狀是我的決定〕

取代 `reference?: string`：

```json
"references": [
  { "source": "kit", "itemId": "k_mia", "image": "ka_3f9x2q.png" },
  { "source": "gen", "genId": "g_88" }
]
```

- `source: "gen"`：手動接到 `in:ref` 的圖片節點，沿用現在「這個 plan 裡已完成的圖片生成」的規則。
- `source: "kit"`：後端從這個 plan 的 `clientId` 找到套組，確認項目和圖片確實屬於這個客戶，否則回 422。這就是反目標「一個客戶的套組圖跑進另一個客戶」的防線。
- 生成紀錄的 `inputs.references` 存當時送出的清單，另外存每個套組項目的 `updatedAt`，「過期」比對就靠這個（§5.4）。生成開始時，把套組圖複製一份到 `media/<ideaId>/gen/` 底下〔我的決定〕，這樣之後刪掉套組項目，舊版本照樣看得到、重跑也有根據。
- `input_hash` 改成把整個 `references` 清單排序後算進去。
- 舊的生成紀錄只有單一 `reference`：讀取時當作 `[{source:"gen", genId: reference}]`，不改寫資料庫〔我的決定〕。

### 4.4 模型清單〔使用者，研究 §3A；只取其中一部分〕

`inputs.reference` 照舊，另外加 `maxRefs: number`。上限要上官方頁面重新核對；研究當天查到的數字：Nano Banana 2 是 14，Nano Banana Pro 是 14（5 人、6 物、3 風格），Seedream 4.5 是 10。研究還建議加 `byRole`（每種類型各自的上限），這次**不做**，用 §5.2 的砍除順序就夠了〔我的決定：只有 Nano Banana Pro 有分類型的上限，為一個模型多一層設定不划算〕。如果某個模型的參考圖會另外收錢，加 `price.perRefUsd`，價格顯示要算進去（目前三個圖片模型看起來都不用）。

## 5. 行為

### 5.1 套組節點與自動接線〔使用者，研究 §3B 選項 A〕

- 畫布工具列的「新增節點」多一個「套組」。每張畫布最多一個〔我的決定〕。
- 節點上顯示這支片的卡司：每個項目一張縮圖、名字和類型標籤。點「編輯套組」會打開套組面板（§6）。
- 新增套組節點後，系統自動從它接一條線到**每一個**分鏡圖節點的新埠 `in:kit`。之後新增的分鏡圖節點（包括 shot list 新增鏡頭時長出來的）也自動接上。使用者可以刪掉某一條，那一鏡就完全不帶套組。
- 為了不讓線蓋住畫布（反目標），套組的線畫成淡色細線，選中套組節點時才變明顯〔交給實作者：React Flow 的 edge style〕。
- 這個節點沒有輸入埠，也不能接到影片節點（§7）。

### 5.2 分鏡圖節點怎麼組參考圖

送出生成時，參考圖依序是：

1. 手動接到 `in:ref` 的圖。`in:ref` 改成可以接多條線，總數不超過模型的 `maxRefs`〔使用者：研究的選項 B，當作底層〕。
2. 套組：`kitItems` 扣掉 `kitOff` 之後的項目，依類型 **角色 → 產品 → 場景 → 風格** 排，每個項目展開成它的所有圖片〔使用者，研究 §3A 的順序〕。

總數超過模型的 `maxRefs` 時，從清單**最後面**開始砍：先砍風格，再砍場景、產品、角色；手動接上的圖最後才砍〔我的決定〕。節點上用一行字說明「這個模型最多 N 張，這次沒帶：Warm film、Shop counter」，生成前就看得到（反目標：不默默丟掉）。

分鏡圖節點上每個套組項目有一個勾選框，取消勾選就寫進 `kitOff`。

### 5.3 Prompt 前綴〔使用者，研究 §3A 和 §2「優先順序 4」〕

後端組 prompt 時，在使用者的 prompt 前面加上固定格式的英文說明。例如：

```
Reference images: image 1–2 are the character "Mia" (early 20s, short black bob, yellow hoodie) — keep her face, hair and outfit the same.
Image 3 is the product "Matcha cup" (white cup, green logo facing camera) — keep its shape, colour and logo the same.
Style: Warm film — 35mm, warm tones, soft light.
```

- 只有文字、沒有圖的風格項目，只產生「Style:」這一行。
- Gemini 和 Seedream 都用同一份前綴，圖片順序就是 `image_urls` 或 `inline_data` 的順序〔我的決定〕。研究說 Seedream 慣用「Figure 1」的寫法；實作者在真實測試時，如果發現「image 1」效果比較差，可以讓各轉接層換成自己的字樣〔交給實作者〕。
- 前綴也算進 `MAX_PROMPT` 長度；超過的話，先把 note 截短。
- 節點上可以展開「實際送出的 prompt」，讓使用者看到前綴〔我的決定〕。

### 5.4 過期〔使用者，畫布規格 §5〕

以下任一件事發生，分鏡圖節點就標 `stale`，下游影片節點也跟著標：
- 套組節點的 `kitItems` 改了；
- 這一鏡的 `kitOff` 改了；
- 這一鏡用到的任何套組項目，`updatedAt` 比這一鏡目前版本記錄的新（換圖或改 note 都算）；
- `in:kit` 的線被接上或刪掉。

不自動重跑。

### 5.5 整條跑完〔我的決定〕

`POST /api/ideas/{id}/gen/chain` 改成分鏡圖那一步也照 §5.2 組參考圖。影片那一步照舊只吃起始畫面。報價照舊。

## 6. 套組面板〔我的決定〕

- 從套組節點的「編輯套組」打開，是畫布上的一個側邊面板（抽屜），不另外做頁面。理由：套組只在畫布上用得到，demo 時不用切換畫面。研究提到的「客戶素材」入口（和品牌放一起），等 P3 品牌面板要搬家時再一起做。
- 面板分兩部分：
  - **這個客戶的套組**：新增、改名、改類型、改 note、上傳或刪除圖片、刪除項目。
  - **這支片要用**：每個項目一個勾選框，對應 `kitItems`。
- 新增項目時，表單只有名字、類型、note 和圖片，上傳完就存。
- 介面文字照規定走 `t()`，英文和繁中都要。
- 寫入套組的路由和品牌一樣，只有登入的員工能用。

## 7. 影片節點：這次不吃套組〔我的決定，使用者可推翻〕

研究的優先順序 3 建議：選了支援參考圖的影片模型（Kling O3、H3 Max、Omni Flash reference-to-video）時，把套組也送進影片。這次不做，原因有三：

1. 目前清單上**沒有**任何影片模型吃參考圖（全部 `reference: none`）。
2. fal 上的 Omni Flash reference-to-video 是另一個端點，**不吃起始畫面**。用了它就不能用分鏡圖當起始畫面，等於放掉研究說的「基本盤」。
3. 研究說，只要分鏡圖一致，起始畫面就足以讓影片一致。這個說法在驗收 demo 的時候順便驗證。

如果驗收時發現影片裡的人走樣，再開一個小階段，加一個吃參考圖的影片模型，影片節點加 `in:kit`。

1. `bash bin/verify.sh` GREEN；`npx tsc --noEmit`、`npm run build`、`npm run lint` 沒有錯誤。
2. 單元測試至少涵蓋：
   - 參考圖組裝的順序和砍除；
   - `kitOff`；
   - 過期的四種觸發；
   - 後端拒絕別的客戶的套組圖；
   - 舊單一 `reference` 的相容讀取；
   - prompt 前綴的格式和截短；
   - `in:ref` 多線與上限。
3. 用 mock 模型在 1440 寬跑一次瀏覽器 E2E：
   - 建立套組（1 個角色＋1 個產品）；
   - 加套組節點，6 個分鏡圖都自動接上；
   - 取消某一鏡的產品；
   - 改角色的 note，確認全部標過期；
   - 整條跑完一鏡。
   - mock 模型也要吃 N 張參考圖，並在佔位圖上印出收到幾張，測試才驗證得到。
4. **真實測試**（要花錢，跑之前先報價）：
   - 同一個客戶的兩個 plan，各 6 鏡，用一個吃參考圖的圖片模型；
   - 人和杯子一眼看得出是同一個；
   - 另外用 Omni Flash 1.1 跑 2 段 4 秒影片，看起始畫面能不能維持長相；
   - 預算：Seedream 4.5 跑 12 張約 US$0.48，加 2 × 4 秒 × $0.10 = US$0.80，共約 US$1.28（用 Nano Banana 2 約 US$1.60）。超過 US$1，**要使用者同意才跑**。

## 9.5 審稿後補的決定（builder check，2026-11-03）

以下都是〔我的決定〕，使用者可推翻。

1. **前端負責組參考圖清單，後端負責檢查和組 prompt 前綴。**
   - 前端照 §5.2 算出 `references[]`（順序、`kitOff`、砍到 `maxRefs`），和現在算 `startFrame` 的方式一樣；「這次沒帶」那一行也由前端顯示。
   - 後端只做三件事：確認每個 `kit` 項目屬於這個 plan 的客戶；確認總數不超過 `maxRefs`，超過就回 422，**不在後端再砍一次**；依 `itemId` 查名字和 note 組前綴。
   - 「整條跑完」的請求也要帶 `references`，前端照同樣的規則算。這樣砍除規則只寫一份（TypeScript），後端不用去讀可能還沒存檔的畫布。
2. **套組項目更新後的過期，在畫布載入時判斷。**
   - 打開畫布時（也包括套組面板存檔之後），比對每個分鏡圖目前版本存的 `references`，以及當時記下的 `updatedAt`，和現在的套組。
   - 有更新、或項目已經被刪掉，就標 `stale`。
   - 不去改寫其他 plan 存著的畫布。
3. **被刪掉的套組項目：**
   - 從 `kitItems` 和 `kitOff` 裡移除，下次存檔就不見了。
   - 有用到它的分鏡圖標過期，節點上寫「Mia 已從套組刪除」。
   - 重新生成就不帶它。生成紀錄裡的副本只給舊版本顯示用，不會被偷偷拿去重跑。
4. **自動接線只在前端做。**
   - 畫布每次載入、以及每次新增分鏡圖節點時，前端幫還沒接上的分鏡圖補上 `in:kit` 線。所以 shot list 在畫布沒打開時新增的鏡頭，下次打開也會接上。
   - 使用者手動刪掉的線不能被補回來：在那個分鏡圖節點記 `data.kitCut = true`，重新接上時清掉。
   - 後端建立畫布的程式不用改。
5. **只有分鏡圖節點有 `in:kit`。** `footage`、`upload`、`video` 都沒有。影片節點的 `in:ref` 照舊依模型判斷能不能接；現有影片模型都是 `reference: none`，所以接不上。
6. **模型限制：**
   - `mock-image` 設 `maxRefs: 14`，佔位圖上印出收到幾張。
   - 選了 `reference: none` 的模型時，`in:kit` 那條線照留，但節點上寫「這個模型不用套組」，生成時不帶參考圖。
   - 有 `reference` 但沒寫 `maxRefs` 的模型，當作 1 張。
7. **價格：** 沒有 `perRefUsd` 就當作 0，報價和現在一樣。
8. **新的節點類型要登記：**
   - 後端：`backend/canvas.py` 的 `NODE_TYPES` 和 `LAYOUT`，以及 `check_doc` 的白名單。
   - 前端：`types.ts` 的 `NodeKind`、`ports.ts` 的 `PORTS`（`kit: { inputs: [] }`，分鏡圖加 `in:kit`）、`outMedia`（kit 輸出新的媒體類型 `kit`，只能接到 `in:kit`）。
9. **`startFrame` 維持單一一張。** `check()` 裡 `startFrame` 和參考圖原本共用 `one(idea_id, id)` 的檢查。改成清單時，只有參考圖改成清單，`startFrame` 不動。
